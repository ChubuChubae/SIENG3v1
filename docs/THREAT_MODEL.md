# SIENG3 — Threat Model

> เอกสารนี้ตอบคำถามเดียว: **ระบบนี้ป้องกันใครจากอะไร และไม่ป้องกันอะไรบ้าง**
> ทุกการตัดสินใจด้าน crypto และ steganography ในโปรเจกต์ต้องอ้างกลับมาที่เอกสารนี้ได้
> เวอร์ชัน 1.0 · Phase 1.1 · อ้างอิง `PROJECT_STRUCTURE.md` §2.6 · `PROJECT_CONTEXT.md` §2.4

## 1. ระบบนี้ปกป้องอะไร

### 1.1 ทรัพย์สินที่ต้องปกป้อง

เรียงตามความเสียหายเมื่อสูญเสีย

| # | ทรัพย์สิน | เสียแล้วเกิดอะไร |
|:--:|---|---|
| A1 | **ข้อเท็จจริงว่ามีการสื่อสารเกิดขึ้น** | นี่คือทรัพย์สินหลักของ steganography — ถ้าผู้ตรวจรู้ว่ามีข้อมูลซ่อนอยู่ ระบบล้มเหลวแล้วแม้จะถอดไม่ได้ |
| A2 | **เนื้อหาของข้อมูลลับ** | ความลับรั่ว |
| A3 | **Identity private key** (Ed25519 · ML-DSA · static X25519 · static ML-KEM) | ปลอมตัวเป็นผู้ใช้ได้ · สร้าง session ใหม่ในนามเขาได้ |
| A4 | **Ratchet state** (chain key + counter) | ถอดข้อความตั้งแต่จุดนั้นเป็นต้นไปได้ทั้งหมด |
| A5 | **ความสัมพันธ์ว่าใครคุยกับใคร** | metadata รั่ว แม้เนื้อหายังปลอดภัย |
| A6 | **ความถูกต้องของผลการทดลอง** | งานวิจัยที่เคลมเกินจริงเสียหายกว่าไม่เคลมเลย |

### 1.2 คุณสมบัติด้านความปลอดภัยที่ตั้งเป้า

| รหัส | คุณสมบัติ | หมายความว่า |
|---|---|---|
| **P1 Undetectability** | ผู้ตรวจแยกไฟล์ที่มีข้อมูลกับไม่มีไม่ออก | วัดเป็น `P_E` ต่อ detector ที่ระบุชื่อ ไม่ใช่คำรับประกัน |
| **P2 Confidentiality** | ถึงรู้ว่ามีข้อมูล ก็อ่านไม่ได้ | AES-256-GCM-SIV + hybrid KEM |
| **P3 Integrity** | ข้อมูลถูกแก้แล้วรู้ | AEAD tag |
| **P4 Sender authentication** | รู้ว่าใครส่งมาจริง | `AUTH_IMPLICIT` หรือ `AUTH_PQ_EXPLICIT` |
| **P5 Replay resistance** | ไฟล์เดิมส่งซ้ำแล้วถูกปฏิเสธ | counter + consumed set |
| **P6 Forward secrecy** | คีย์ปัจจุบันหลุด ข้อความเก่ายังปลอดภัย | symmetric ratchet + zeroize |
| **P7 Carrier binding** | ตัด payload ไปแปะภาพอื่นแล้วถอดไม่ได้ | AAD ผูกกับ `carrier.fingerprint()` |
| **P8 Post-quantum confidentiality** | ข้อมูลที่ดักไว้วันนี้ถอดไม่ได้แม้มี quantum computer | ML-KEM-768 |

## 2. ฝ่ายตรงข้าม

### 2.1 ตารางฝ่ายตรงข้าม

| # | ฝ่ายตรงข้าม | ทำอะไรได้ | เป้าหมาย | ในขอบเขต |
|:--:|---|---|---|:---:|
| **T1** | **Passive warden** | เห็นทุกไฟล์ที่ส่ง · รัน steganalysis ระดับ state of the art (DCTR, GFR, SRNet) · มีทรัพยากรคำนวณสูง | รู้ว่ามีข้อมูลซ่อนอยู่ (A1) | **ใช่** |
| **T2** | **Active warden** | ทุกอย่างของ T1 + แก้ไข บีบอัดซ้ำ ครอบตัด หรือตัดต่อไฟล์ระหว่างทาง | ทำลายข้อมูล หรือหลอกให้ผู้รับยอมรับของปลอม | **ใช่ (ตรวจจับได้)** |
| **T3** | **Network MITM** | สลับ public key ตอนตั้ง session · สร้าง session แยกกับทั้งสองฝั่ง | อ่านทุกอย่างตรงกลาง (A2, A5) | **ใช่** |
| **T4** | **Harvest now, decrypt later** | เก็บทุกไฟล์ไว้วันนี้ · มี quantum computer ในอนาคต | ถอดข้อมูลย้อนหลัง (A2) | **ใช่** |
| **T5** | **File-system attacker** | อ่าน เขียน คัดลอก ย้อนไฟล์ state บนเครื่องผู้ใช้ (ไม่ได้ควบคุม process) | บังคับให้ counter ซ้ำ (A4) | **บางส่วน** |
| **T6** | **Malicious file supplier** | ป้อนไฟล์ที่ออกแบบมาโจมตี parser ของ analyzer | RCE หรือใช้ทรัพยากรจนเครื่องล่ม | **ใช่** |
| **T7** | **Curious recipient** | เป็นผู้รับที่ถูกต้อง แต่อยากรู้เกินขอบเขต | หา identity ของผู้ส่งคนอื่น หรือความลับที่ไม่ได้ส่งให้ตน | **ใช่** |
| **T8** | **Endpoint compromise** | ควบคุม process · อ่าน RAM · ฝัง keylogger · แก้ binary | ทุกอย่าง | **ไม่** |
| **T9** | **Coercion / rubber-hose** | บังคับผู้ใช้ให้เปิดเผยคีย์ด้วยกฎหมายหรือกำลัง | ทุกอย่าง | **ไม่** |

### 2.2 ทำไม T8 กับ T9 อยู่นอกขอบเขต

**T8 Endpoint compromise** — ถ้าผู้โจมตีควบคุม process ได้ เขาอ่านคีย์จาก RAM ได้ก่อนที่ `zeroize()` จะทำงาน แก้โค้ดให้ส่งคีย์ออกไปได้ หรือรอ keylogger เก็บรหัสผ่านได้ ไม่มีอะไรในระดับ application ที่กันเรื่องนี้ได้ และ **Python ไม่รับประกันการล้างหน่วยความจำอยู่แล้ว** (`bytes` เป็น immutable · GC ทิ้งสำเนาได้ · OS swap ลงดิสก์ได้) การเคลมว่าป้องกันได้จึงเป็นการหลอกตัวเอง

**T9 Coercion** — ระบบนี้ไม่มี deniability ไฟล์ stego ที่มี header ถอดได้ถูกต้องคือหลักฐานว่ามีการฝังจริง เมื่อผู้ตรวจได้คีย์มา การจะกันเรื่องนี้ต้องออกแบบ deniable encryption ซึ่งเป็นคนละระบบและมีข้อจำกัดในทางปฏิบัติมาก

**สิ่งที่ต้องทำแทน:** ประกาศให้ชัดใน README, ใน `SECURITY.md` และในหน้า about ของ GUI ว่าสองอย่างนี้อยู่นอกขอบเขต ผู้ใช้ที่ threat model จริงมี T8 หรือ T9 ต้องรู้ว่าเครื่องมือนี้ไม่ตอบโจทย์เขา

## 3. แยกคำศัพท์ให้ชัด

สี่คำนี้ถูกใช้ปนกันบ่อยจนกลายเป็นการเคลมที่ผิด หัวข้อนี้กำหนดความหมายที่ใช้ตลอดทั้งโปรเจกต์

### 3.1 นิยาม

| คำ | นิยามที่ใช้ในโปรเจกต์นี้ | ระบบนี้มีไหม |
|---|---|:---:|
| **Forward secrecy (FS)** | คีย์ที่ใช้ ณ เวลา `t` หลุด แต่ข้อความก่อนเวลา `t` ยังถอดไม่ได้ **โดยมีเงื่อนไขว่าคีย์เก่าถูกลบสำเร็จจริง** | **มี** |
| **Post-compromise security (PCS)** | หลังคีย์หลุดแล้ว ระบบกลับมาปลอดภัยได้เองเมื่อผู้โจมตีหยุด active | **ไม่มีใน Phase 1** |
| **Key compromise** | ผู้โจมตีได้ **คีย์** ไป (identity key, chain key, message key) แต่ไม่ได้ควบคุมเครื่อง | อยู่ในขอบเขต ผลกระทบตาม §3.3 |
| **State compromise** | ผู้โจมตีได้ **ไฟล์ ratchet state** ไป — ซึ่งบรรจุ chain key ปัจจุบัน + counter | อยู่ในขอบเขต เท่ากับ key compromise ของ chain key |

**ความต่างที่คนพลาดบ่อยที่สุด:** FS มองย้อนหลัง PCS มองไปข้างหน้า
ระบบนี้มี FS แปลว่า *อดีตปลอดภัย* — ไม่ได้แปลว่า *อนาคตปลอดภัย*

### 3.2 ทำไม Phase 1 ยังไม่มี PCS

PCS ต้องมีการนำความลับใหม่เข้ามาในระบบเป็นระยะ ซึ่งทำได้ด้วย re-KEM (รัน KEM ใหม่แล้วผสมเข้า chain)
Phase 1 มีแค่ **symmetric ratchet** ซึ่งเป็น one-way function chain — เดินหน้าได้อย่างเดียว ไม่มีความลับใหม่เข้ามา
ผู้โจมตีที่ได้ `CK[n]` จึงคำนวณ `CK[n+1]`, `CK[n+2]`, … ได้ตลอดไปโดยไม่ต้องทำอะไรเพิ่ม

แผน: `crypto/rekey/` มีที่วางไว้แล้ว จะทำใน Phase 2 (`PROJECT_CONTEXT.md` §12.3 · P2-1)

### 3.3 ตาราง scenario × protection

ช่องที่เขียนว่า **ป้องกันไม่ได้** คือส่วนที่สำคัญที่สุดของเอกสารนี้

| # | Scenario | ป้องกัน | เหตุผล |
|:--:|---|:---:|---|
| S1 | ขโมย **message key เก่า** `MK[n]` | **ได้** | `MK[n]` มาจาก `HKDF(CK[n], "msg")` ย้อนกลับหา `CK[n]` ไม่ได้ และเดินหน้าไม่ได้เพราะ label ต่างกัน |
| S2 | ขโมย **chain key เก่า** ที่ zeroize แล้ว | **ได้** | ค่าไม่มีอยู่ในหน่วยความจำหรือดิสก์แล้ว |
| S3 | ขโมย **chain key ปัจจุบัน** `CK[n]` | **ไม่ได้** | ถอดข้อความ `n` เป็นต้นไปได้ทั้งหมด — นี่คือขอบเขตของ FS |
| S4 | ขโมย **ไฟล์ ratchet state** | **ไม่ได้** | เท่ากับ S3 · ไฟล์ถูกเข้ารหัสด้วย AEAD แต่คีย์ที่ห่อมันอยู่บนเครื่องเดียวกัน |
| S5 | ขโมย **private KEM key** | **ไม่ได้** | สร้าง session ใหม่ในนามผู้ใช้ได้ · แต่ session เก่าที่ใช้ ephemeral key ยังปลอดภัย |
| S6 | ขโมย **identity signing key** | **ไม่ได้** | ปลอมตัวได้จนกว่าจะ revoke — ต้องมีกลไก revoke ที่ผู้รับตรวจจริง |
| S7 | **MITM ตอนตั้ง session** | **ได้** | `AUTH_IMPLICIT` ผูก static-static DH เข้า transcript · ผู้ไม่มี static private key คำนวณ `ss` ไม่ได้ |
| S8 | **Replay** ไฟล์เดิม | **ได้** | counter + consumed set ใน `RecvChain` |
| S9 | **แก้ ciphertext** | **ได้** | AEAD tag |
| S10 | **ตัด payload ไปแปะภาพอื่น** | **ได้** | AAD ผูกกับ `carrier.fingerprint()` |
| S11 | **บีบอัดซ้ำ / ย่อ / ครอบตัด** ระหว่างทาง | **ตรวจจับได้ ไม่ได้กู้คืน** | payload หายทั้งหมด · robustness เป็น non-goal |
| S12 | **State rollback** โดย T5 | **ลดความเสียหายได้ ไม่ได้ป้องกัน** | ดู §4 |
| S13 | **Endpoint compromise** | **ไม่ได้** | นอกขอบเขตโดยประกาศ (T8) |
| S14 | **Coercion** | **ไม่ได้** | นอกขอบเขตโดยประกาศ (T9) |
| S15 | **Post-compromise recovery** | **ไม่มีใน Phase 1** | ต้องมี re-KEM |
| S16 | **Parser RCE จากไฟล์ต้องสงสัย** | **ลดความเสียหายได้** | container ที่ตัด network + จำกัดทรัพยากร (`PROJECT_STRUCTURE.md` §4.8) |
| S17 | **Decompression bomb / DoS** | **ได้** | input limit ก่อนถึง parser + resource cap ของ container |
| S18 | **Steganalysis** โดย T1 | **วัดผลได้ ไม่ได้รับประกัน** | J-UNIWARD + STC + selection channel ต่อไฟล์ · รายงานเป็น `P_E` |

## 4. State rollback — พูดตรงๆ ว่าป้องกันได้แค่ไหน

### 4.1 ปัญหา

```
counter = 100          Process A อ่าน state -> counter 101
  |  สำรองไฟล์ state   Process B อ่าน state -> counter 101
counter = 101 (ส่งภาพ)      |             |
  |  คืนค่าที่สำรองไว้    ทั้งคู่ใช้ MK[101] กับ plaintext คนละอัน
counter = 100 -> ใช้ MK[100] ซ้ำ
```

ทั้งสองทางจบที่เดียวกัน: **message key ตัวเดียวถูกใช้กับ plaintext สองอัน**

### 4.2 ความจริงที่ต้องยอมรับ

**ถ้าผู้โจมตีเขียนไฟล์บนเครื่องได้ การ rollback ป้องกันแบบสมบูรณ์ไม่ได้ด้วย state ที่เก็บในไฟล์เพียงอย่างเดียว**
เขาสำรองแล้วคืนค่ากลับได้เสมอ การอ้างว่าป้องกันได้เป็นการเคลมเกินจริง

### 4.3 สามชั้นที่ทำได้จริง

| ชั้น | กลไก | ป้องกันอะไร | ข้อจำกัด | เฟส |
|:---:|---|---|---|:---:|
| 1 | **Monotonic generation counter** ในไฟล์ state + ตรวจว่าไม่ลดลง | ผู้ใช้ restore backup โดยไม่ตั้งใจ · cloud drive sync ทับ | ผู้โจมตีที่ตั้งใจย้อนได้ | 1 |
| 2 | **Exclusive lock** ครอบทั้ง read-modify-write | สอง process ทำงานพร้อมกัน | ไม่กัน rollback | 1 |
| 3 | **Monotonic counter ระดับ OS/hardware** (TPM NV counter · Keychain · DPAPI) | rollback แบบตั้งใจ | ผูกกับแพลตฟอร์ม · ย้ายเครื่องยาก | 2 |

### 4.4 ตาข่ายนิรภัยชั้นสุดท้าย

นี่คือเหตุผลที่เลือก **AES-256-GCM-SIV ไม่ใช่ GCM ธรรมดา** ตั้งแต่ต้น

| | key+nonce ซ้ำแล้วเกิดอะไร |
|---|---|
| AES-GCM | **รั่ว authentication key `H`** → ผู้โจมตีปลอม tag ได้ทุกข้อความในคีย์นั้น = หายนะ |
| AES-GCM-SIV | เสียแค่ความสามารถบอกว่า "plaintext สองอันนี้เหมือนกันหรือไม่" = เสียหายแต่ไม่ล่มสลาย |

การออกแบบที่ถูกต้องคือยอมรับว่าชั้น 1–2 กันความผิดพลาดได้ ชั้น 3 กันเจตนาร้ายได้บางส่วน และ **เลือก primitive ที่ทนทานเมื่อทั้งสามชั้นล้มเหลว**

## 5. สมมติฐานที่ระบบตั้งอยู่บน

ถ้าข้อใดข้อหนึ่งไม่จริง ความปลอดภัยของระบบไม่เป็นไปตามที่เอกสารนี้บอก

| # | สมมติฐาน | ถ้าไม่จริงจะเกิดอะไร |
|:--:|---|---|
| A-1 | ผู้ใช้เทียบ **fingerprint** ของคู่สนทนาผ่านช่องทางที่เชื่อได้ก่อนเริ่มคุย | MITM (T3) สำเร็จทันที · authentication ทั้งหมดไม่มีความหมาย |
| A-2 | เครื่องของผู้ใช้ไม่ถูกควบคุมโดยผู้โจมตี | ทุกอย่างล้มเหลว (T8) |
| A-3 | `carrier/image/jpeg.py` เขียนกลับได้ **byte-exact** เมื่อไม่แก้ค่า | double compression ทำให้ DCTR/GFR จับได้ตั้งแต่ยังไม่ฝังอะไร — P1 ล้มเหลว |
| A-4 | ML-KEM-768 และ X25519 ปลอดภัยตามที่มาตรฐานอ้าง | P2/P8 ล้มเหลว |
| A-5 | ไลบรารี crypto ที่ใช้ implement ถูกต้อง (ไม่ implement เอง) | P2/P3/P4 ล้มเหลว |
| A-6 | ผู้ใช้ไม่ส่งไฟล์ stego ผ่านช่องทางที่บีบอัดซ้ำ | payload หาย (S11) |
| A-7 | cover image เป็นภาพจริงที่ไม่เคยเผยแพร่ที่อื่นมาก่อน | ผู้ตรวจเทียบกับต้นฉบับได้ = จับได้ทันทีโดยไม่ต้องใช้ steganalysis |
| A-8 | ผู้ใช้ไม่ใช้ cover เดิมซ้ำหลายครั้ง | ผู้ตรวจเทียบไฟล์สองเวอร์ชันแล้วเห็นความต่างโดยตรง |

> **A-7 กับ A-8 เป็นความรับผิดชอบของผู้ใช้ที่โค้ดบังคับไม่ได้** แต่ GUI ควรเตือนเมื่อเห็นว่ากำลังใช้ cover ที่เคยใช้ไปแล้ว

## 6. Known gaps

ประกาศไว้ให้ชัดดีกว่าปล่อยให้เข้าใจผิด ทุกข้อต้องปรากฏใน `MANIFEST.json` ของทุก release ด้วย

| # | Gap | เหตุผลที่ยังไม่แก้ | แผน |
|:--:|---|---|---|
| G1 | **Post-compromise security** | ต้องมี re-KEM ซึ่งเปลี่ยนโครง session | Phase 2 (P2-1) |
| G2 | **Rollback โดยผู้โจมตีที่ตั้งใจ** | state ในไฟล์ย้อนได้เสมอ ต้องพึ่ง counter ระดับ OS | Phase 2 (P2-2) |
| G3 | **Memory compromise** | Python ล้างหน่วยความจำไม่สมบูรณ์ | ประกาศเป็นนอกขอบเขต |
| G4 | **C-level memory bug ใน libjpeg** | `atheris` เข้าถึงได้แค่ชั้น Python | ชดเชยด้วย sandbox · Phase 2 ใช้ libFuzzer (P2-4) |
| G5 | **PQ sender authentication แบบไม่ใช้ signature** | ข้อจำกัดของ ML-KEM เอง ไม่ใช่ของการออกแบบนี้ | ใช้ `AUTH_PQ_EXPLICIT` เมื่อความจุอำนวย |
| G6 | **Robustness ต่อการบีบอัดซ้ำ** | ขัดกับเป้าหมาย undetectability โดยตรง | non-goal ถาวร |

## 9. เมื่อไหร่ต้องกลับมาแก้เอกสารนี้

- เพิ่ม carrier ที่ `security_tier` ไม่ใช่ `strong` → เพิ่ม scenario ใหม่ใน §3.3
- ทำ re-KEM เสร็จ → G1 ปิด · §3.1 เปลี่ยนคำตอบของ PCS
- เปลี่ยน crypto suite → ทบทวน §5 ทั้งหมด
- เพิ่มการส่งไฟล์ผ่านเน็ตเวิร์ก → **ต้องเขียน threat model ใหม่ทั้งฉบับ** เพราะ attack surface เปลี่ยนโดยสิ้นเชิง (และเรื่องนี้เป็น non-goal ถาวร)
